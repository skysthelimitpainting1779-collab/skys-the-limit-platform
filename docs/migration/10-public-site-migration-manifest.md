# Public-Site Migration Manifest

## Migration rule

**Clone the rendered product, not the old application architecture.** The production website supplies public design, brand, content presentation, SEO, conversion UX, verified assets, responsiveness, and accessibility work. The platform supplies the canonical Next.js/Convex/WorkOS architecture. Directus, Payload, legacy Supabase CMS/admin paths, `/manage`, old adapters, old agent harnesses, stale dependencies, and obsolete package scripts are explicitly excluded.

## Asset and interaction inventory procedure

The implementation does not start from source copying. For each public route, capture desktop, tablet, and mobile screenshots; headings, landmarks, metadata, canonical URL and redirects; visible assets and font use; hover/focus/scroll states; client interactions; form transitions; and network requests. Create a route specification with a source-of-truth content classification: verified fact, approved marketing copy, user-generated evidence, or unknown.

Every asset must have provenance, license/ownership, optimized output format, alt text, and a platform destination. The platform uses its own optimized asset pipeline and does not retain source-code dependencies simply because an old component referenced an asset.

## Estimate-intake migration contract

The multi-step conversion experience becomes a canonical form, not a copied legacy implementation. The secure flow is:

```text
User -> client validation -> controlled API or Convex boundary
     -> payload size limits + honeypot + idempotency + server timestamp
     -> narrow public intake mutation -> lead/opportunity records
     -> authorized durable follow-up workflow
```

The public mutation can create only a limited intake record. It cannot choose an organization, set internal statuses beyond a safe initial state, assign a role, access CRM search, write estimates/jobs, or invoke privileged workflow actions. UTM data and consent evidence are stored as validated input; model/business interpretation happens later through authorized operations or workflows.

## SEO and quality gate

Each public-route slice needs semantic heading hierarchy, metadata, canonical/redirect review, sitemap/robots source-of-truth verification, keyboard navigation, visible focus, contrast, responsive screenshots, image alternative text, and production/preview smoke checks. Do not carry duplicate sitemap or robots implementations into the platform.

## Cutover prerequisite

Public-site migration may only begin after the platform authorization foundation protects operational data and the CMS foundation supports published structured content. The website remains live until route-by-route parity is verified and the rollback origin remains ready.
